### 1.1 原生只读静态逆向的扩面授权（2026-10-21）

原 §3 第 1 条把 `videoeditor.dll` 限定为「只作调用对象」。2026-10-21 用户明确扩大动作面，
目标是「**整体逆向，获取框架结构和格式信息**，针对外置草稿工具提供参考支持」，并给出硬约束
「**不会改造 dll**」。据此放开**只读静态**面，其余禁令原样保留。

| 项 | 内容 |
|---|---|
| 允许 | 对原生二进制的**只读静态**分析：反汇编、反编译伪代码、符号表/类型/RTTI、字符串与 PE 资源枚举、交叉引用、调用图 |
| 目的限定 | 只为**结构与格式**取证（类型名、字段名、枚举取值、序列化布局、容器结构）。产出回答「剪映自己写了什么」，不回答「怎么脱离剪映自己算出密钥」 |
| 仍然禁止 | 加密算法还原与密钥提取（§3 第 1 条保留句）；修改/补丁/hook/注入 DLL 的任何形式；运行时调试器附加与断点（§7 保留）；任何产物分发（§3 第 2 条保留） |
| 执行方式 | REA 的 Ghidra provider（Windows P0 只读边界，26 个只读操作）。REA **import 不可变副本**做静态分析，不把 DLL 载入分析进程、不执行其入口例程，源文件只读 |
| 产物落点 | 反汇编/伪代码原文只落 `temp/rea-native/`（被根仓库 `.gitignore` 忽略，不进 git 历史）；写进 `docs/` 的只有**结构级结论**与 `文件:行号`/地址级出处，不整段贴伪代码 |
| 资源例外 | §4 的 2 GB 内存硬上限是为本项目的预览服务与语料扫描定的，**不约束** Ghidra headless；Ghidra 侧单独用 `GHIDRA_HEADLESS_MAXMEM` + `REA_GHIDRA_STARTUP_TIMEOUT_MS` 设预算，且必须先在小目标上冒烟、再对 72 MB 目标做单次可行性判定并记录实测 RSS 与耗时 |

扩面只改「能不能读」，不改「能不能写」：§3 第 4、5 条（不改安装目录、M1 不写草稿）原样有效。

2. **不分发**任何解密/破解工具或算法；解密只在用户本机、只对用户自有草稿发生。
3. **不绕过**许可、DRM、账号校验或任何授权机制；不使用他人草稿。
4. **不修改**剪映安装目录下的任何文件（全程只读）。
5. **不写草稿**：M1 全程只读草稿；解密产物只落 `temp/`，绝不写进草稿目录。写回能力属 M3，且必须先过回环门禁。
6. **不复制**参考实现代码：`jianying-editor-skill`（MIT）的代码只读不抄，本项目脚本里不得出现其复制片段，也不得在运行时 import 它；引用只以文件路径形式出现在 `docs/evidence/findings.md`。

## 6. 证据纪律

采用 `reverse-skill` 的 Evidence → Finding → Path 格式，逐条记入 `docs/evidence/findings.md`。三路证据交叉：

1. 静态分析（REA）——JS 侧用 `analyze-javascript-application` 取 `canvas_agent` 的字段与枚举定义；
   原生侧自 2026-10-21 起按 §1.1 用 Ghidra provider 取类型/RTTI/字符串表与序列化布局；
2. 语料统计——本机草稿全量的形态与频次（口径与快照日期见 `corpus-scan.md`，r3 = 按去重内容计）；
3. 成片比对——`<DRIVE_E>/输出` 的剪映真实导出反推数值语义；
4. **探针实测**——浏览器解码轴与服务端出图轴（F-036~F-046 落在 `temp/px-probe/`，脚本、行值、配置三样齐全）。
   这一路有自己的纪律：**每个数写明二进制绝对路径、重复次数与分母口径**，
   能力探测必须用被测对象自己产出的配置记录（F-044 的教训）。

结论分级：**已验证**（≥2 路独立证据一致）/ **单源待验证** / **未解决**。与第三方资料（`jianying-editor-skill/references`、`capcut-cli docs/draft-schema`、`pyJianYingDraft`）冲突时，**一律以本机剪映语料实测为准**，冲突记入 `docs/evidence/conflicts.md`。

### 6.1 两路证据的分工（2026-10-21 由用户定调，F-049/F-050/F-052 的做法由此固定）

「剪映程序自己写了什么」（安装包内的代码与协议文档）与「用户的草稿里实际有什么」（r3 语料）**不是同一种事实**，
谁为准要分场景，不许一刀切：

| 要判的事 | 以谁为准 | 为什么 |
|---|---|---|
| 字段**叫什么名**、哪些值**合法**、某个键**能不能写**、单位与量纲的定义 | **程序自身**（代码 + 协议 schema） | 语料只能证明「出现过」，不能证明「合法」，也不能证明「没别的写法」 |
| **实际缺省值**、频次、取值范围、这个功能在本机到底用没用过 | **语料实测** | 代码里的默认值属于哪条写入路径，只有语料能回答 |
| 某结构**是否存在**、是否会被剪映接受 | **语料实测**（阴性结论要写清是「语料未见」而非「不存在」） | 同上 |

三条附身规矩（都是本轮真踩过的）：

1. **逐条标来源**。凡引用程序侧证据，要写到 `文件:行号` 级；凡引用语料侧，要写清计数口径（多少份内容 vs 多少次）。
2. **agent 面的默认值禁止回填桌面草稿**。`Resources/canvas_agent` 是 **11.6 新增的 web/agent 写入面**
   （`package-manifest.json` 自报 `platform="darwin-arm64"`，`app-server.mjs` 写 `version=400000 / os="web"`），
   它的默认值不等于桌面编辑器历代缺省 —— 实测反例：`check_flag` 模型默认 63 而语料众数 **39**，
   `alignment` 模型默认 1 而 11.6 桌面**整键缺席**。
3. **两边对不上是一种结论，不是「语料错了」**。`render_index` 的分配规则（代码给得出）解释不了语料次带的奇偶与空洞
   ⇒ 正确写法是「还有第二个写入者没找到」（U-63），**不许**据此把语料里真实存在的 496 条判成非法再「规范化」掉。

这条分工与 §6 原句不冲突：原句管的是**第三方资料**（CapCut 时代文档、别人逆向）vs 本机语料 —— 那种一律语料为准；
本节管的是**剪映自己的程序**vs 本机语料 —— 按上表分场景。
