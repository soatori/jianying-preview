# 与既有资料的冲突及裁定

裁定原则：**与第三方资料冲突时一律以本机剪映语料实测为准**。（限定 2026-10-21：本条只管**外部资料** vs 本机语料。**剪映自己的程序** vs 本机语料属另一类问题，按 `scope.md` §6.1 分场景——名称/合法性以程序为准，缺省值/频次/值域以语料为准。C-013 就是这一类。）外部资料（CapCut 为主的 capcut-cli、5.9 时代的 pyJianYingDraft）只作交叉参考，引用需署名。
- `jianying-editor-skill`（MIT，上游 luoluoluo22，本机 fork `1.7.0+crypto-ops.1`）：只读参考，不复制、不运行时依赖。
- `renezander030/capcut-cli` `docs/draft-schema/*`（MIT）：交叉参考。
- `GuanYixuan/pyJianYingDraft`（Apache-2.0）：5.9 时代字段语义参考。

| C-001 | `uniform_scale` 位置 | capcut-cli：属于 clip，且常为 `{on:true}` | 51,718 个 segment 中 `uniform_scale` 作为 **segment 级** 字段出现 34,843 次（r3；缺席 16,875、值为 null 4,325）；`clip` 内从未出现该键（`clip_fields.csv` 只有 transform/flip/scale/rotation/alpha）。**位置之争采信语料，形态之争改判**：capcut-cli 的 `{on:true,value}` 形态确实存在（`{on:true,value:1.0}` 12,467 条），另有 `{}` 18,010 / `{on:false}` 35 / 仅 `value` 若干，是两套写入形态并存，不是一种形态（详见 F-023） | 语料 |

| C-011 | `materials.speeds[]` 到底是不是「无值 stub」 | 本项目 C-002 与 `spec/materials.yaml`、`spec/picture.yaml` 曾写「speeds 多为无值 stub，真实倍速只在 `segment.speed`」；另一说是 capcut-cli 的「speeds 承载变速包络」 | r3 口径 29,376 个 speeds 条目：**17,696 个不带 `speed` 键**（这类才是 stub）、8,293 个 `speed == 1`、**3,387 个带非 1 的真实倍速**；凡片段 `speed` 有值且引用到 speeds 条目处，`speeds[].speed == segment.speed` **11,680 / 11,680 全部相等，0 例外**；`speed != 1` 的片段**全部**有 speeds 镜像（无镜像的 7,923 个片段倍速都是 1）。曲线包络另在 `speeds[].curve_speed`（9,109 条）与 `speeds[].mode`（{0: 8810, 1: 298}），与「stub」说法无关 | 语料：`segment.speed` 仍是权威，`speeds[].speed` 是它的**忠实镜像**（可以整键缺席，但存在时必然相等）。写回若改倍速必须同步该镜像 → `spec/write-rules.md` §3、F-023 |
| C-012 | 「Chrome 不支持 HEVC」 | 广泛流传的外部说法（含 Windows 上 Chrome 需硬件解码器/系统扩展的论述），以及**本项目 F-038 自己的实测**：`hvc1` 的 `isConfigSupported` 两种 profile 都 false、`<video>` 零帧 | 带 GPU 的 headless Chrome（ANGLE = GTX 1650）里，用**该文件自己导出的 hvcC**（113 字节，`hvc1.1.60000000.L153`）探测，四个 `hvc1` 串全 True，同一条 4K60 HEVC 真解出 241 帧、播放 60.08 fps；把 `description` 换成 4 字节假值则全 False（F-044） | **本机实测**：HEVC 可用，前提是硬件解码通路开启。原「必须预转码」的降级要求降为边界处理；但失败形态仍是静默的（`videoWidth=0`、不触发 `error`），显式降级判定保留 |
| C-013 | `Resources/MixMode/MixMode.json` 的 `nameId` 能不能当混合模式语义用 | 剪映自己的资源索引写 `nameId: "color_filter"` → `path: d9c1d4ca7ab91df4f48d12b339f2da88`；而协议枚举里 `color_filter`（= 展示 schema 的「颜色滤镜」）与 `screen`（=「滤色」）是**两个不同的模式**；同一个包 md5 的 GLSL 尾行是 `ScreenBlendPreMul`，而 r3 语料里指向该包的片段 `effects[].name` 写的是「滤色」（37 次 / 22 份内容） | `nameId` **不能**当语义用。两路独立证据（包内 GLSL 函数名 + 草稿内联中文 `name`）都说 `d9c1d4ca…` 是**滤色 / screen**，所以 `MixMode.json` 里 `color_filter` 只是内部键名（9 条 nameId 与 GLSL 函数名语义吻合，唯独这一条不吻合）。可直接 join 的键是 `resourceId` / `effectId` / `path`，全部实测 **166/166 命中、0 未匹配**；`nameId` 只可作旁注。附带结论：协议枚举 12 个模式、本机资源索引只有 10 个包，缺的正是 **差值(difference)** 与 **颜色滤镜(color_filter)**（`tables/mixmode_packages.csv`，F-049） | 语料 + 包内 GLSL（不采信 nameId） |
